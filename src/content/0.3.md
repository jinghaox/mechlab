MuJoCo (Multi-Joint dynamics with Contact) is a physics engine built for robotics. You describe a robot in a text file, and MuJoCo computes how it moves under gravity, motor torques and contacts. It is fast, accurate and free, and it is what you will use for nearly every robotics lab in this course.

In the last lesson you wrote the differential equation yourself and handed it to `solve_ivp`. MuJoCo does both jobs: it derives the equations of motion from your description of the mechanism, then integrates them.

## Describing a model: MJCF

A model is written in an XML format called MJCF. Here is a complete pendulum:

```xml
<mujoco model="pendulum">
  <option timestep="0.002" gravity="0 0 -9.81" integrator="RK4"/>

  <worldbody>
    <body name="pendulum" pos="0 0 0">
      <joint name="hinge" type="hinge" axis="0 1 0" damping="0"/>
      <geom name="rod" type="capsule" fromto="0 0 0  0 0 -0.5" size="0.01" mass="0.02"/>
      <geom name="bob" type="sphere" pos="0 0 -0.5" size="0.05" mass="1"/>
    </body>
  </worldbody>
</mujoco>
```

Four elements carry almost all of the meaning:

| Element | What it is |
|---|---|
| `<body>` | a rigid body. Bodies nest: a child body moves with its parent, which is how you build an arm link by link. |
| `<joint>` | a degree of freedom between a body and its parent. A `hinge` rotates about `axis`; a `slide` translates along it. A body with no joint is welded to its parent. |
| `<geom>` | shape and mass attached to a body. Geoms define what collides and what the body weighs. |
| `<option>` | global settings: the time step, gravity and the integrator. |

Later you will add `<actuator>` elements (motors) and `<sensor>` elements. Units are SI throughout: metres, kilograms, seconds, radians.

So this file says: one body, hanging from the world by a hinge about the $y$ axis, made of a light 0.5 m rod with a 1 kg ball on the end. The $z$ axis points up.

## Model and data

MuJoCo splits everything into two objects, and keeping them apart in your head makes the API easy to read.

```python
import mujoco

model = mujoco.MjModel.from_xml_string(xml)   # or from_xml_path("file.xml")
data = mujoco.MjData(model)
```

- **`model`** holds what does *not* change during a simulation: masses, link lengths, joint axes, the time step.
- **`data`** holds what *does* change: the current time, positions, velocities, forces.

The fields of `data` you will use most:

| Field | Meaning |
|---|---|
| `data.time` | simulation time in seconds |
| `data.qpos` | generalized positions: one entry per joint coordinate |
| `data.qvel` | generalized velocities |
| `data.ctrl` | actuator commands, which you write |
| `data.sensordata` | readings from the model's sensors |

For the pendulum, `qpos` and `qvel` each have a single entry: the hinge angle in radians and its rate in rad/s. A 6-joint arm has six of each. The pair (`qpos`, `qvel`) is the **state** of the system, the same $x$ as in $\dot{x} = f(t, x)$.

## The simulation loop

```python
data.qpos[0] = 0.5          # start at 0.5 rad
mujoco.mj_forward(model, data)

while data.time < 10.0:
    mujoco.mj_step(model, data)
```

`mj_step` advances the state by one time step. Each call computes the accelerations from the current state and forces, then integrates to get the new `qpos` and `qvel`.

`mj_forward` computes everything that depends on the state, such as body positions and energy, **without** advancing time. Call it after you set `qpos` by hand, so that the derived quantities match the state you just wrote.

When you add a controller in Module 2, it goes inside this loop: read `data.qpos` or `data.sensordata`, compute a command, write it to `data.ctrl`, then step. That is the feedback loop from lesson 0.1, in four lines.

## The time step matters

The `timestep` option is how far each `mj_step` moves forward. A smaller step is more accurate but slower. Too large a step makes the simulation inaccurate and, with stiff systems or contacts, unstable. Values from 0.001 to 0.005 s are typical for robot arms. The choice of integrator matters too: `RK4` is very accurate for smooth systems like this pendulum, while the default `Euler` is cheaper and good enough for most models with contact. You will measure the difference in the lab.

## Seeing it move

MuJoCo ships with an interactive viewer. Running `python -m mujoco.viewer` opens an empty one that you can drag an XML file into. From a script, `mujoco.viewer.launch_passive(model, data)` opens a window that displays the state while your own loop does the stepping; the lab has a short example.

=== frc ===

MJCF plays the role that CAD plus your robot's constants file play in FRC: it is the single description of what the mechanism is. `data.qpos` corresponds to your encoder positions, `data.ctrl` to the values you send to motor controllers, and one pass through the simulation loop corresponds to one 20 ms `periodic()` call, only here the time step is 2 ms and the robot cannot break. WPILib's own physics simulation classes do the same job for single mechanisms; MuJoCo does it for whole robots with contact.

=== summary ===

- An MJCF model is built from **bodies** connected by **joints**, with **geoms** giving shape and mass.
- `model` is constant; `data` is the changing state. The state is (`qpos`, `qvel`).
- `mj_step` advances time by one `timestep`; `mj_forward` recomputes derived quantities without advancing.
- A controller reads from `data`, writes `data.ctrl`, then steps.
- Time step and integrator trade accuracy against speed.
